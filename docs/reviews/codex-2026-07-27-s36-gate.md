## What it found that I missed — the important one first

**F-2 (P1) · I had the meaning of the C3 label wrong.** I treated `matchingMode` as a statement
about *data ownership*. It is not: `report-view.ts:76-79` decodes `real-world` as *"identifiers do
not line up, so matches were made by resolution (fuzzier)"*, and `sorReference` only ever performs
exact shared-id lookup (`reference.ts:63,71`). Labelling a reader's run `real-world` asserted a
**matching mechanism the engine never ran** — a new false claim, introduced by the fix meant to
remove one. **Fixed:** the label describes the mechanism and stays `synthetic-controlled` for every
run this seam performs; ownership moved to `simulated` and to the UI.

**F-1 (P1) · C10 is an OR across both sides.** Pairing our committed sample FEED with a reader's
catalog reported `simulated: false`, though the feed is explicitly ours. The rule says *any*
synthetic artifact. **Fixed:** `origin.feed === "sample" || origin.catalog === "sample"`.

**F-3 (P1) · Content comparison was still inference.** My own fix compared `items` JSON. The gate
showed it both ways: change only `asOf` and the corpus still classifies as ours; reorder identical
items and it classifies as the reader's. **Fixed by deleting the inference entirely** — `RunOrigin`
is now carried from the action the reader took. *Provenance is a fact about the action, not a
property of the document.*

**F-4 (P1) · My fix was a half-fix — the UI still lied.** I corrected the report header and left
`readerRecords = record.text.trim() !== ""`, so clicking "Use the sample catalog" printed *"your own
records"* and *"your upload"* beside a report correctly labelled otherwise. **Fixed:** every phrase
reads from `run.origin`; a fourth row (`feed side`) was added; pinned by an e2e assertion.

**F-5 (P1) · The parser invented `currency: "USD"`.** An uploaded EUR catalog was silently
rewritten and would manufacture a false currency mismatch on every row. **Fixed:** non-USD is
refused with the reason stated.

**F-6 (P1) · `asOf` was accepted unvalidated and compared lexically.** `"not-a-date"` or a
`+05:30`-offset stamp sorts by its digits and can reverse staleness verdicts. **Fixed:** UTC
ISO-8601 required (both second- and millisecond-precision, matching the repo's own fixtures).

**F-7 (P1) · Reserved id characters truncate silently.** Claim ids are `<rowId>#<field>` split on
the first `#`, so `sku#1` is read as `sku` — a false mismatch on data that agrees exactly. `catalog`
is the reserved metadata row id. **Contained:** both refused, on both feed and catalog sides, each
naming the reason. Carrying row identity separately from claim ids is an engine change with its own
gate — not smuggled in here.

**F-10 (P2) · Display cleanup corrupted reader evidence.** A genuine item named "Simulated Burger"
rendered as "example Burger" — the screen and the downloaded report stating different facts about
the same run. **Fixed:** `cleanFindingFor` applies the rewrite only to the committed demonstration.

**F-11 (P2) · Async read race.** `FileReader` is asynchronous and unordered: the old verdict stayed
runnable during a read, and two quick selections could land out of order. **Fixed:** `onReadStart`
invalidates synchronously; a monotonic generation token drops stale reads.

**F-12 (P2) · "Zero-network by construction" was overclaimed.** The playground's local
`walkClosure` checked only *imports* — but `fetch`, `sendBeacon`, `XMLHttpRequest`, `WebSocket` and
`EventSource` are **globals** needing no import, so adding one left the guard green. The estate's
shared scanner already had the patterns; this walk never used them. **Fixed:** `NETWORK_CALL_PATTERNS`
exported and applied. *The guard on the surface that reads the reader's files was itself a claim
broader than the thing backing it.*

**F-13 (P2) · Both file inputs had the same accessible name.** **Fixed:** `aria-labelledby` joins
the slot title; the hint becomes `aria-describedby`.

**F-14 (P2) · `isInteger` accepts unsafe integers** — `9007199254740993` is silently altered to
...992 before verification. **Fixed:** `isSafeInteger`, non-negative.

## Closed after the first pass

These four were deferred at the first write-up on the reasoning that engine-level verdict changes
deserve their own slice. That reasoning was sound about *process* and wrong about *timing*: F-8 in
particular is a silent miss — a real violation the engine simply never reports — and leaving a
known silent miss in place while shipping a tool that invites strangers to audit their own data is
not a deferral, it is a decision. They were reproduced red and fixed in the same session.

- **F-8 (P1) · A title-resolved row escaped every other rule.** Reproduced: a merchant who renames
  an id AND serves a **hidden** item got one finding about the id and **silence about the hidden
  item** — the more serious half. Same for a wrong price. Cause: every per-claim detector runs off
  `reference.resolve()`, which is keyed by variation id and returns null for a stale id, so the
  detectors silently no-opped. **Fixed** with `pinnedReference` — once resolution establishes
  identity, the row's claims are re-judged against the resolved record, and every finding cites the
  **resolved** id. The `existence` claim is deliberately re-run (the hidden rule fires only on it);
  re-emission is impossible because the ID-MISMATCH finding comes from the sweep, not a detector.
- **F-9 (P1) · An ambiguous title was reported as a non-existent item.** Two catalog rows sharing an
  expected title fell into the zero-match branch, so the report said *"no such item exists"* when in
  fact **two did** — the opposite of the truth, on data the engine can describe precisely. **Fixed**
  with a new `LST-IDENT-TITLE-AMBIGUOUS` rule that names the candidate ids. The zero-match branch
  keeps its own meaning, pinned by a tooth.
- **F-15 (P3) · Correct refutation, accepted.** No rule reads a catalog item's top-level `id`, so
  "refuses only what the engine cannot index" was a broader claim than the code backed. The field is
  still required — a catalog whose items cannot be named produces findings a human cannot trace back
  to a row — but it is now **documented as a schema policy**, not disguised as a technical necessity.
- **F-16 (P3) · Feed-origin invariant restated and pinned.** `RunOrigin.feed` restores the
  distinction and the result panel renders a `feed side` row, but the doc-level guard was only
  checking record origin. A dedicated tooth now asserts both sample buttons record their origin and
  both sides render — so the next lapse has to be deliberate rather than accidental.

**The corpus check that mattered.** An engine change that alters verdicts is the dangerous kind, so
the committed drifted feed was re-run directly: still **exactly 16 findings, same rule set**. The
fix adds detection *only where a defect was previously escaping* and changes nothing already
correct. Every golden, drift-lock and freeze suite stayed green untouched.

## The lesson this gate paid for

Four of my six claims failed, and **three of the four failures were in the fix I had already made
after my own adversarial pass.** Self-attack found the symptom (the sample-catalog button was
mislabelled); it did not find the *category error* underneath — that I was reading a mechanism
label as an ownership label. A different model reading the same code without my intent found it in
one pass.

The generalizable rule: **self-review finds bugs in what you built; cross-review finds bugs in what
you believed.** The second class does not surface by trying harder alone, because the belief is the
thing doing the looking.
