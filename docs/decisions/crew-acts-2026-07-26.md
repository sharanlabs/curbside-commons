# Should the crew ACT rather than recommend?

**Scoped 2026-07-26** on the owner's "latest agentic AI product" directive · analysis + recommendation
· **owner-gated: no code follows from this document.**

## The question

The crew (`intake` · `audit` · `evidence` · `reviewer`) currently produces **recommendations** that
terminate in one of two states: a `recommendation` a human reads, or `escalate-to-human`. It never
takes an action. "Latest agentic AI product" could reasonably mean it should — that a modern agentic
system *does things* rather than proposing them.

## Recommendation: **NO for the audit path. YES, narrowly, for a new operator path.**

Not a compromise — the two halves rest on different arguments and land in different places.

## Why not on the audit path

**1. The product's value IS the refusal to act.**

The README's whole thesis: every seat in the delivery chain has a conflict of interest, so a credible
referee must sit outside them. A referee that also *acts* has acquired a stake. The moment this
system can amend a feed, issue a credit, or file a dispute, "independent verifier" stops being true —
and that sentence is the product.

This is not a safety hedge dressed as principle. It is the same reason the engine, not the model,
decides every verdict: the deterministic core is the thing worth trusting, and the agents are
explicitly the *untrusted* layer around it (`lib/crew/` quarantines artifact content, forces
escalation on anomalies, and pins the engine report hash precisely because a model touched the run).
Letting that layer act inverts the architecture.

**2. `RULES.md` §3 already answers it, in order.**

> 11. Decision before action.
> 12. Human approval before risky automation.

The ordering is the ruling. An acting crew puts action before human approval on a path where the
inputs are attacker-controllable — which is the M2 injection work from two days ago: artifact content
reaching a model is treated as hostile *by design*. An agent that can act on hostile input is a
prompt-injection payload's delivery mechanism. The tripwire that currently forces escalation would
become the only thing between an injected instruction and a real-world effect, and that tripwire was
demonstrably bypassable **twice this week**.

**3. The honest agentic claim is already available and already true.**

"Agents recommend, the engine decides" is a *stronger* position than "agents act," not a weaker one —
it is the harder engineering problem and the more defensible product. The current surface (7 MCP
tools, 4-role crew, forced-escalation path, recommend-only lanes) is genuinely agentic. What it lacks
is not capability but **framing** — which is the positioning work, not an architecture change.

## Where "act" is legitimate: a separate, owner-armed operator path

There is a real capability gap, and it is not in the audit lane. Today a human who receives a finding
must act entirely outside this system. A narrow **operator path** could close that without touching
the referee property:

- **Scope:** act only on the *output* of a completed, human-approved audit — never inside the audit.
- **Actions:** compose and send the notification that already exists (`lib/delivery/`), open a
  tracking record, schedule a re-check. All reversible; none touches the engine, the report, or a
  verdict.
- **Gate:** the existing L-2 one-shot pattern — owner-armed per invocation, one action per arming,
  allowlisted destination, no retry path, redacted run record written before the irreversible step.
  That pattern already survived four real sends and a dedicated guard suite.
- **Hard exclusions:** never amends a feed or catalog · never issues money · never files with a
  regulator · never runs unattended · never acts on an artifact that tripped the injection scan.

That is "agentic" in the sense that matters — a system that closes the loop — while the *judgment*
stays deterministic and the *action* stays owner-gated.

## What I am NOT proposing

- No standing infrastructure. `CLAUDE.md`'s prototype-not-a-service identity holds; every action is
  an on-demand, labeled demonstration.
- No autonomy. "Owner-armed per invocation" means exactly that; a queue that drains itself is a
  different decision.
- No action inside the audit path, under any framing.

## If the owner wants the full version anyway

That is a legitimate call — it is the owner's product. It would require, at minimum, and *before* any
code: re-opening `RULES.md` §3 (11) and (12) as an explicit amendment with its own decision row, not
a quiet reading; a threat model for acting on attacker-controllable input; and a pre-registered eval
for action correctness, because "the agent did the right thing" is a claim this repo would need to
measure rather than assert. I would want the K≥3 consistency run scored first — an agent whose
terminals flip is not one to hand actions to, and we do not yet know whether these flip.

## Status

**No code. No RULES change.** The recommendation is: keep the audit path recommend-only, take the
positioning work now (it is what the directive most likely wants and costs no safety), and treat the
operator path as a scoped follow-on the owner may authorize on its own merits.
